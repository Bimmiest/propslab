# Dependencies

## The engine and its regex engine

The engine is the [`propslab-engine`](https://github.com/Bimmiest/propslab-engine) package, and both `package.json` files depend on it by commit. It owns the pin of [`pcre2-wasm-utf16`](https://github.com/Bimmiest/pcre2-wasm-utf16), the PCRE2 WebAssembly module, and its checksum ([ADR 0023](adr/0023-the-engine-moves-to-a-repository-of-its-own.md)). The app still declares the module itself, because it imports the module's asset URL, and the MCP server copies the binary into its build.

To take a new release of the engine, in one pull request:

1. Move the `propslab-engine` commit in both `package.json` files to the commit of the release's tag.
2. Move the `pcre2-wasm-utf16` commit in both files to the commit that the engine's `package.json` declares.
3. Run `npm install` in the root and in `packages/mcp-server`, and the gates.

`server.e2e.test.ts` fails when the two `package.json` files or the two lockfiles differ, or when the regex engine's pin differs from the engine's. Both lockfiles record a GitHub dependency as `git+ssh://git@github.com/...#<commit>`, with no integrity hash. That is how npm writes every GitHub dependency, and no `package.json` spelling changes it. It is not what an install does: npm fetches such a dependency over https first (the commit's tarball, then a clone), so CI needs no ssh key. With no hash in the lockfile, `scripts/check-wasm-checksum.mjs` verifies the binary against the `pcre2.wasm.sha256` that the module ships, and against the one that the engine ships, in every job that installs it.

## Supply-chain checks

`supply-chain.yml` watches what Dependabot cannot. It runs `npm run check:overrides` (the `overrides` below against what the lockfile resolves) on pull requests that touch `package.json`, the lockfile or `.nvmrc`, and monthly. Monthly it also compares `.nvmrc` with the newest release on its Node line (shared-workflows' `node-patch-check`) and fails when it is behind; on a pull request that check only annotates. The deploy attests the `dist/` it uploads, in a job with the signing permissions and nothing else, and refuses to upload anything the attestation does not cover; the comments in `azure-static-web-apps.yml` say what that proves and what it does not. To check a deployed bundle later, `gh attestation verify` the `dist.sha256` manifest from that run's `dist-attestation` artifact (kept 30 days) with `--signer-workflow`.

Every production dependency's licence is on `.licence-allowlist.json` (`packages/mcp-server/.licence-allowlist.json` for the server's lockfile), or the package is named there with the version somebody read and why it is acceptable; `pcre2-wasm-utf16` is, because the PCRE2 licence's attribution condition is met by `NOTICE`. A bump past a named version fails until the new version is read too.

**Read the lockfile diff of each Dependabot pull request.** A nested copy, such as `+ "packages/mcp-server/node_modules/<package>"`, tells you that the top level cannot take that version. `npm ci` then installs the package with a peer dependency that is not satisfied, and the checks can stay green. To correct this, run `npm dedupe`, or update the related packages in one change.

**Do not fix a group on the Dependabot branch.** If one package of a group merges separately, Dependabot closes the group, deletes its branch and opens a new group. Put the fix on a `chore/` branch from `origin/main`, and close the group as superseded.

## The Radix packages

Fourteen exact `@radix-ui/*` pins used to sit in `overrides` ([#147](https://github.com/Bimmiest/propslab/issues/147), [#152](https://github.com/Bimmiest/propslab/pull/152)). `cmdk` asks for older caret ranges of the primitives (`react-primitive` `^2.0.2`, `react-dialog` `^1.1.6`, `react-id` `^1.1.0`, `react-compose-refs` `^1.1.1`) than `react-dialog`, `react-tooltip` and `react-context-menu` resolve to. When the lockfile held older versions, npm hoisted `cmdk`'s copies and nested a second copy of each primitive under every current Radix package, and the bundle shipped both. Those ranges now accept the versions that the current Radix packages pin, so `cmdk` shares them. We checked this ([#776](https://github.com/Bimmiest/propslab/issues/776)) by removing the pins one at a time, and all at once. With the lockfile, and without it, npm resolved one copy of each package, and the lockfile did not change. `src/__tests__/dependencyPins.test.ts` fails when a Radix package has a nested copy in the lockfile. If it fails, run `npm dedupe`. If that does not help, add an override for the version that `react-dialog` resolves to, and add a row for it to the table above. Check by hand with `npm ls @radix-ui/react-primitive`: each line but the first says `deduped`.

Three overrides remain. One is `typed-rest-client` → `qs`. `@stryker-mutator/core` 10 asks for `typed-rest-client ~2.3.0`, which pins `qs` 6.15.1 exactly, and that version carries denial-of-service advisories (GHSA-q8mj-m7cp-5q26, GHSA-x5fp-wj9c-mxmx, GHSA-4mjr-xmp4-gh2g). The override lifts it to a fixed release; drop it once Stryker depends on a `typed-rest-client` whose own `qs` is fixed.

Another is `monaco-editor` → `dompurify`. `monaco-editor` 0.57 declares `dompurify` 3.4.15 exactly, and that version carries GHSA-p98j-92pf-mc4p, GHSA-cg2g-xh64-v4q7 and GHSA-mrv2-3pqr-j5jr. The override lifts the declared package to 3.4.17, the first release past all three, and because the declaration is an exact pin Dependabot cannot do that on its own. **The override does not change what ships.** Monaco does not import the `dompurify` package: it inlines its own copy (`esm/vs/base/browser/dompurify/dompurify.js`, version 3.4.15). The override only takes the advisory off the `npm audit` and Trivy reports. What makes the inlined copy safe here is that no hover sets `supportHtml`, so Monaco drops raw HTML before the sanitiser sees it, and every one of these advisories needs markup to exploit. The only trusted hover (`splunkConfHover.ts`) enables one command and escapes the document text it quotes. Keep it that way: if a provider starts to set `supportHtml`, or builds trusted Markdown from document text, these advisories become reachable. Drop the override once a `monaco-editor` release inlines a fixed `dompurify`.

The third is `minimatch`, for the whole tree. `minimatch` 10 carries GHSA-g3hv-75wg-m249, and only 11 fixes it. `eslint`, `@eslint/config-array`, `@typescript-eslint/typescript-estree` and `@stryker-mutator/core` ask for 10 even in their latest releases, so they run on 11 outside the range that they declare. They call only `minimatch()`, `Minimatch` and `MinimatchOptions`, which 11 keeps. The override needs `eslint-plugin-import-x` 4.18.1 or later: an earlier one imports `makeRe`, which 11 removed, and ESLint stops. `npm run check:overrides` does not see an override for the whole tree, so drop it by hand when all four ask for 11 ([#944](https://github.com/Bimmiest/propslab/issues/944)).

All three overrides are caret ranges (`^6.16.0`, `^3.4.17`, `^11.0.8`), so the next fix within the major reaches the lockfile through `npm update` or a Dependabot lockfile update. An exact pin would leave a later advisory red on every pull request until someone edits `package.json`. `npm run check:overrides` fails once no copy of the parent asks for an older version than the override. That is when to drop it.
