# Dependencies

The supply-chain checks, the regex engine's binary, the overrides, and how to review a Dependabot pull request. [CONTRIBUTING.md](../CONTRIBUTING.md#dependencies) has the summary.

## The regex engine's binary

The module lives in its own repository, [`Bimmiest/pcre2-wasm-utf16`](https://github.com/Bimmiest/pcre2-wasm-utf16), and this one depends on it by commit (`package.json`), not by tag: a tag can be moved, a commit hash cannot. That repository commits `pcre2.wasm`, built from a pinned PCRE2 release with clang 18 and `wasm-ld`, and its CI rebuilds it and fails unless the result is byte-identical, so the binary is known to come from the source. To change it — a PCRE2 upgrade, a bridge change — make the change there, tag a release, and move the commit in `package.json` here and in `packages/mcp-server/package.json`, which declares it too (a test in the package fails while the two differ). Copy the new `pcre2.wasm.sha256` of the release to the root of this repository in the same change. Thus the reviewer sees the hash change (#567). Both lockfiles record the dependency as `git+ssh://git@github.com/...#<commit>`, with no integrity hash. That is how npm writes every GitHub dependency, and no `package.json` spelling changes it (tried: the `git+https://` form resolves to the same line). It is not what an install does: npm fetches such a dependency over https first (the commit's tarball, then a clone) and tries ssh only after that fails, so CI needs no ssh key; checked by running `npm ci` with ssh unavailable. With no hash in the lockfile, two copies of `pcre2.wasm.sha256` vouch for the binary: the copy in the package and the copy at the root of this repository. `scripts/check-wasm-checksum.mjs` verifies the binary against both in every job that installs it.

## Supply-chain checks

`supply-chain.yml` watches what Dependabot cannot. It runs `npm run check:overrides` (the `overrides` below against what the lockfile resolves) on pull requests that touch `package.json`, the lockfile or `.nvmrc`, and monthly. Monthly it also compares `.nvmrc` with the newest release on its Node line (`scripts/check-node-patch.mjs`) and fails when it is behind; on a pull request that check only annotates. The deploy attests the `dist/` it uploads, in a job with the signing permissions and nothing else, and refuses to upload anything the attestation does not cover; the comments in `azure-static-web-apps.yml` say what that proves and what it does not. To check a deployed bundle later, `gh attestation verify` the `dist.sha256` manifest from that run's `dist-attestation` artifact (kept 30 days) with `--signer-workflow`.

Every production dependency's licence is on `.licence-allowlist.json` (`packages/mcp-server/.licence-allowlist.json` for the server's lockfile), or the package is named there with the version somebody read and why it is acceptable; `pcre2-wasm-utf16` is, because the PCRE2 licence's attribution condition is met by `NOTICE`. A bump past a named version fails until the new version is read too.

**Read the lockfile diff of each Dependabot pull request.** A nested copy, such as `+ "packages/mcp-server/node_modules/<package>"`, tells you that the top level cannot take that version. `npm ci` then installs the package with a peer dependency that is not satisfied, and the checks can stay green. To correct this, run `npm dedupe`, or update the related packages in one change.

**Do not fix a group on the Dependabot branch.** If one package of a group merges separately, Dependabot closes the group, deletes its branch and opens a new group. Put the fix on a `chore/` branch from `origin/main`, and close the group as superseded.

## The Radix overrides

The exact `@radix-ui/*` pins in `package.json`'s `overrides` dedupe the Radix primitives ([#147](https://github.com/Bimmiest/propslab/issues/147), [#152](https://github.com/Bimmiest/propslab/pull/152)). `cmdk` asks for older ranges of them than `react-dialog`, `react-tooltip` and `react-context-menu` resolve to, and without the overrides npm hoisted cmdk's copies and nested a second copy of each primitive under every current Radix package — both shipped, since they are distinct files (about 12 kB gzip at the time). The pinned versions are the ones `@radix-ui/react-dialog` pins exactly, directly or through its own dependencies. When you bump a Radix package, move the overrides to the versions it pins, and check with `npm ls @radix-ui/react-primitive` that there is still one copy.

Two overrides are not Radix. One is `typed-rest-client` → `qs`. `@stryker-mutator/core` 10 asks for `typed-rest-client ~2.3.0`, which pins `qs` 6.15.1 exactly, and that version carries denial-of-service advisories (GHSA-q8mj-m7cp-5q26, GHSA-x5fp-wj9c-mxmx, GHSA-4mjr-xmp4-gh2g). The override lifts it to a fixed release; drop it once Stryker depends on a `typed-rest-client` whose own `qs` is fixed.

Nor is `monaco-editor` → `dompurify`. `monaco-editor` 0.57 declares `dompurify` 3.4.15 exactly, and that version carries GHSA-p98j-92pf-mc4p, GHSA-cg2g-xh64-v4q7 and GHSA-mrv2-3pqr-j5jr. The override lifts the declared package to 3.4.17, the first release past all three, and because the declaration is an exact pin Dependabot cannot do that on its own. **The override does not change what ships.** Monaco does not import the `dompurify` package: it inlines its own copy (`esm/vs/base/browser/dompurify/dompurify.js`, version 3.4.15). The override only takes the advisory off the `npm audit` and Trivy reports. What makes the inlined copy safe here is that no hover sets `supportHtml`, so Monaco drops raw HTML before the sanitiser sees it, and every one of these advisories needs markup to exploit. The only trusted hover (`splunkConfHover.ts`) enables one command and escapes the document text it quotes. Keep it that way: if a provider starts to set `supportHtml`, or builds trusted Markdown from document text, these advisories become reachable. Drop the override once a `monaco-editor` release inlines a fixed `dompurify`.

Both non-Radix overrides are caret ranges (`^6.16.0`, `^3.4.17`), so the next fix within the major reaches the lockfile through `npm update` or a Dependabot lockfile update. An exact pin would leave a later advisory red on every pull request until someone edits `package.json`. `npm run check:overrides` fails once no copy of the parent asks for an older version than the override. That is when to drop it.
